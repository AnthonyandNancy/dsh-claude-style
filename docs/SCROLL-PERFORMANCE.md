# 滚动卡顿的根因与整改方案

本文件回答：插件已经装好，页面静止时没有异常，读者滚动长会话时仍然掉帧；在不改变功能、动画、界面与样式的前提下，要把这类卡顿降到可接受范围，应当改哪些地方、为什么这些改动不改变读者看到的结果、以及用什么读数验收。

本文件保留证据、根因、方案与验收，不记录施工进度。机制写在模块头注释里，方向性选择写在 `docs/adr/`，可执行的规则写进构建、lint 与测试；长会话与流式输出的常规优化仍由 `docs/PERFORMANCE.md` 负责，本文件只处理它没有覆盖的滚动路径。

## 结论摘要

卡顿不是常驻动画占满合成器造成的。同一条长会话空闲 2 秒时，调度器一次也没有被唤醒，滚动的帧间隔中位数仍是 16.8 毫秒；问题出在滚动这条输入触发的三段成本叠加：

1. 滚动和窗口尺寸变化共用同一个理由 `viewport`。每次滚动都会请求一次整页调度通行，并把 `reposition('viewport')` 派发给所有实现了这个钩子的功能；一次 4 秒滚动里出现 52 次通行，常规通行调用 8 个测量句柄和 16 个同步句柄。
2. 窗口滚动与窗口尺寸变化共用同一个 `reposition('viewport')`，所有定位句柄都被唤醒，关闭的卡片也要先判断一次打开状态。`view-tabs` 的 `measure()` 每次通行都读取 8 个盒，其中 6 个由它自己的 `view-tabs` 代码读取、2 个由它调用的共享滑块读取；Windows 标题栏模式下这些位移读数不参与任何写入，仍然照常执行。滚动样本里，这 8 次读取占盒读取总数的 30%。
3. 构建把 72 个样式表拼成一张常驻样式表，约 1609 组选择器、约 41 万字符。滚动时的强制样式重算要为可视节点重复匹配整张表，样式表因此成为放大器；样式表开关对照里样式阶段下降约 45%，同一对照的绘制阶段上升约 47%，脚本阶段基本不变，所以这一项只能证明样式表参与总成本，不能单独解释卡顿。

整改由三项互不替代的工作组成：

- 把滚动与窗口尺寸变化分开，滚动不再触发整页通行；只有窗口尺寸变化才走原来的整页重定位。
- 窗口滚动只重定位已打开的表面；关闭的表面不被调用，窗口尺寸变化仍走整页路径。
- 样式表按页面与表面分片挂载，规则本身、顺序与优先级保持不变。

三项分别减少唤醒次数、无用测量与样式匹配规模。任何一项单独完成都只覆盖一段成本，三项都完成后，滚动路径只承担本次滚动真正改变的画面。

## 证据与边界

所有读数来自同一台机器、同一棵树、同一份构建产物。样本是 8 轮填充后的 40 行会话，共 2464 个页面节点、约 11.8 千像素的会话高度。滚动脚本为每 35 毫秒一次滚轮、方向每 12 步反转，持续 3 至 4 秒；宿主由 `packages/testing/dsh-web.mjs` 启动，浏览器是本机 Chrome。CPU 节流只在明确写出的阶段开启。采样脚本保留在 `.debug/scroll-evidence/`：`scroll-profile.mjs` 读空闲与滚动的帧间隔和渲染器计数，`scroll-passes.mjs` 读每通行功能调用次数，`scroll-callers.mjs` 读盒读取与文档查找的调用者，`scroll-stacks.mjs` 读调用链，`scroll-forced.mjs` 读强制样式与布局，`scroll-trace.mjs` 读样式表开关对照，`scroll-cpu.mjs` 读 CPU 取样。

- 空闲无通行、滚动有通行，是直接对照。
- 每次通行 8 个测量句柄、16 个同步句柄，以及皮肤自己的 376 次盒读取（其中 282 次有完整调用链）和它们的调用位置，是页面自己计数与调用链归属的直接读数。这 376 次读取全部落在读阶段；样本里没有出现写阶段的皮肤盒读取。
- 样式表开关对照只能说明样式表参与滚动成本，不能把 45% 的样式下降直接换算成帧时间收益；同一对照里绘制阶段上升，说明移除样式改变了绘制路径。
- 4 倍节流用于暴露余量，不代表真实机器上每一帧都会超过 33 毫秒；验收仍以同机前后对照为准。

## 根因一：滚动被当成窗口尺寸变化

**现场**：`packages/engine/src/scheduler.ts` 在 `window` 上以捕获方式监听 `scroll`，窗口尺寸变化与滚动进入同一个处理函数。该函数排出一个包含测量与重写的帧，派发 `measureReposition()` 与 `reposition('viewport')`，并调用 `schedule({ reason: 'viewport' })`。于是会话滚动器内部的一次滚动，会走完整页调度，并让所有声明了 `viewport` 或没有声明 `wakesOn` 的功能获得一次通行。

**为什么这不合理**：窗口尺寸变化会改变列宽、换行、卡片宽度与标题栏布局；会话滚动只改变内容在滚动容器里的位置，不改变任何固定表面的锚点。当前代码没有区分这两件事，滚动付出了尺寸变化的代价。

**直接后果**：样本里 48 个滚动步骤产生 52 次通行；常规通行调用 8 个测量句柄和 16 个同步句柄。`reposition('viewport')` 的 9 个实现中，账户页脚、模型选择器、档位选择器与权限卡片只在该表面打开时才读取盒，关闭时只做一次判断；输入卡、统计、聊天跟随、聊天折叠与对话导航仍会在每次滚动时执行自己的一段工作，其中输入卡与统计还会另排一帧测量输入卡宽度。调度器为这些判断与工作付出每次滚动的固定成本。

**改法**：

- 把 `scroll` 与窗口尺寸变化拆成两个来源：`scroll` 只表示内容在容器内移动，`viewport` 只表示窗口尺寸变化。
- `scroll` 不再调用 `schedule()`，不再请求整页通行；它只派发 `reposition('scroll')`，并且只在滚动确实可能移动已打开表面的锚点时派发。
- `resize` 保持现有路径：测量、重定位与 `schedule({ reason: 'viewport' })` 都保留。
- `FeatureHandle.reposition` 的 reason 扩为 `'scroll' | 'viewport' | 'composer'`；每个实现按自己的表面处理，未处理的原因直接返回。
- 会话滚动器内部的滚动按“锚点是否在容器内”分流，不做一刀切：账户页脚、模型与档位控件、权限卡片、主菜单、输入卡与统计面板的锚点都在滚动容器之外，不派发重定位；对话导航的轨道就在滚动容器里，它保留自己的滚动监听来更新当前标记，不再经整页通行重复读取；聊天等待行的固定位置由 `position: sticky` 在滚动容器内完成，不需要写阶段重算。窗口滚动仍保留重定位路径。

**为什么可见结果不变**：窗口尺寸变化仍走原来的整页路径，所有依赖尺寸的布局与今天相同。会话滚动时，锚点在容器外的固定表面本来就不随内容移动，跳过重定位不改变任何可见像素；对话导航的当前标记仍由它自己的滚动监听更新，滚动时每一帧的标记与今天一致；聊天等待行的 `sticky` 仍由浏览器完成。滚动位置仍只由滚动主人写，读者接管与跟随让开的语义不变。

**验收**：

- 机制层规范：会话滚动器上派发一次 `scroll`，调度通行次数为 0，皮肤盒读取为 0；派发一次窗口滚动，已打开表面得到一次 `measureReposition()` 与 `reposition('scroll')`，关闭表面不被调用；派发一次 `resize`，全部句柄的 `measureReposition` 与 `reposition('viewport')` 都执行，且通行原因仍为 `viewport`。
- 端到端 `readerScroll`、`doorPin`、`streamPace` 与 `longSession` 通过。
- 新滚动场景里，会话滚动导致的功能调用与盒读取从基线降到 0；窗口滚动与窗口尺寸变化的读数与改动前一致。

## 根因二：窗口滚动把每个定位句柄都叫醒

**现场**：调度器为滚动与窗口尺寸变化共用同一个 `reposition('viewport')`，所有实现了 `reposition` 的句柄都会收到这一帧，不论它的卡片是否打开。`view-tabs` 的 `measure()` 也每次都读取条带子节点、标题候选、标题栏、操作区，并通过共享滑块读取活动项与控制框，共 8 个盒；它的 `sync()` 随后在 Windows 标题栏模式下直接返回，因此其中用于位移的读数在桌面窗口里不参与任何写入。滚动样本中的 376 次皮肤盒读取全部来自这里，并且都发生在读阶段。

**为什么这会放大**：

- 会话滚动不会改变标题栏、输入卡宽度或侧栏宽度，重复测量得到的值与上一帧相同，却仍要为它付出盒读取与强制布局。
- 关闭的卡片本来没有像素，却仍要在每个窗口滚动事件里执行一次打开判断；打开的卡片在写阶段读取锚点，读取之后跟着写入，会让浏览器把这一帧已经写脏的整页重新排版。
- `context-stats` 的 `reposition('viewport')` 无条件调用 `inline.refit()`，后者另排一个帧读取输入卡宽度；`composer` 的 `reposition` 无条件调用 `responsive.measure()`，后者也另排一个帧读取卡片宽度。滚动时这些读取与额外帧都不产生新的可见结果。

**改法**：

- 窗口滚动只通知声明跟随自身的打开表面：账户页脚、模型与档位卡片、权限卡片、首页菜单、上下文面板与聊天跟随按钮各自在表面打开时才读取并对齐；关闭的表面不被调用。
- `view-tabs` 在 Windows 标题栏模式下跳过位移测量，只保留分段控件滑块需要的活动项测量；该模式下的位移由样式表固定放置。
- 窗口尺寸变化仍走原来的整页路径：`measureReposition()`、`reposition('viewport')` 与调度通行都保留，关闭的表面也在下一次打开时读到新尺寸。
- 会话滚动按事件目标分流：滚动发生在会话容器内时既不唤醒通行，也不重定位容器外的固定表面；滚动发生在窗口或其他控件上时保留重定位。

**为什么可见结果不变**：打开的表面仍在同一帧重新定位，关闭的表面本来就没有像素；窗口尺寸变化仍唤醒每个句柄，所有依赖尺寸的布局与今天相同。Windows 标题栏模式下的位移本来就不使用测量结果，跳过它不改变固定位置。分段控件滑块仍按活动项测量，滑动动画的起点、终点与曲线不变。

**验收**：

- 机制层规范：窗口滚动只调用打开表面的 `measureReposition()` 与 `reposition('scroll')`，关闭的表面不被调用；窗口尺寸变化仍调用全部句柄。
- 滚动场景里皮肤盒读取为 0；窗口尺寸变化场景里各表面位置与改动前一致。
- 端到端 `readerScroll`、`streamPace`、`doorPin` 与 `motion` 通过，固定行与跟随位置没有可见跳动。

## 根因三：全量常驻样式表放大每次强制重算

**现场**：`scripts/build.mjs` 把主题样式表与各功能清单登记的样式表按 rank 拼成一张主样式表，随客户端一起挂到页面。源码里有 72 个样式表、约 1609 组选择器；构建出的主样式表约 41 万字符。设置页、首页、弹层、输入卡与侧栏的规则都在同一张表里，滚动时浏览器为可视节点重新匹配全部规则。

**证据与边界**：在同样开启 4 倍节流的滚动里，移除皮肤样式表后，每一步的样式阶段从 70.0 毫秒降到 38.1 毫秒，脚本阶段从 20.1 毫秒到 19.9 毫秒基本不变；绘制阶段从 29.7 毫秒升到 43.7 毫秒。这说明样式重算的规模与皮肤表有关，也说明移除样式会改变绘制路径，不能把样式阶段的差值直接当成帧时间收益。因此这一项列为放大器，而不是唯一的根因。

**改法**：

- 构建把每个样式表作为独立片段写入产物，运行时按原始 rank 顺序创建 `<style>` 占位标签，先不填内容；某个页面或表面需要时再填入对应片段，离开时清空内容。标签顺序不变，因此规则之间的先后与优先级不变。
- 片段按页面与表面分组：常驻的令牌、排版、窗框与共享基础规则始终挂载；设置页、首页、弹层、输入卡、侧栏与对话列的规则只在对应页面或表面出现时挂载。
- 不修改任何选择器、声明、时长、颜色、圆角与层级；不改变动画的时长、曲线、循环次数与起止位置。
- 分组依据使用页面上已有的标记：宿主阶段、设置对话框、弹层与抽屉的打开状态、输入卡与侧栏的存在。没有新增读者可观察的开关，也不改变偏好默认值。

**为什么可见结果不变**：片段只在对应的页面或表面出现时进入样式表，规则文本与顺序不变；同一页面上的计算样式与今天相同。关闭的表面本来就没有像素，它的规则不参与匹配不会改变任何可见结果。页面切换时，先挂载新页面的片段，再移除旧页面的片段，避免切换帧短暂丢失样式。

**验收**：

- 行为层：设置页、首页、弹层、输入卡、侧栏与对话列在打开和关闭前后的盒、计算样式、层级与动画读数与改动前一致。
- 外观快照：`appearance.json` 已登记的部分与改动前一致；`shots` 场景的明暗两套截图一致；`importance` 场景通过，`!important` 的覆盖面没有变化。
- 滚动场景：同脚本下活动规则数下降，样式阶段耗时下降，帧 p95 与超过 33 毫秒的帧数不高于改动前。
- 动画：`motion` 与 `washLine` 通过，动画名称、层数、时长、曲线与循环次数不变。

## 三项整改的关系

| 整改项 | 减少什么 | 不减少什么 |
| --- | --- | --- |
| 分开滚动与窗口尺寸变化 | 会话滚动带来的整页通行、定位派发与无关功能调用 | 已打开表面仍需的窗口滚动重定位；样式匹配规模 |
| 窗口滚动只重定位打开的表面 | 关闭卡片的判断、已打开卡片在写阶段的锚点读取与写后读造成的整页重排 | 窗口尺寸变化时的必要测量；规则数量 |
| 样式表分片挂载 | 滚动时参与匹配的规则数量 | 已打开表面的重定位；必要的盒读取 |

三项各自可以独立验收，不存在先后依赖；全部完成后，滚动路径只承担“本次滚动真正改变的画面”。

## 改动边界

- 不新增 `MutationObserver`、`ResizeObserver` 或 `requestAnimationFrame`；新的观察与排帧仍走 `packages/engine/src/bus.ts` 与 `packages/engine/src/frame.ts`。
- 不新增对宿主服务的按名读取；需要新数据时在 `packages/engine/src/host.ts` 加访问器，并在 `packages/contracts/src/table.ts` 登记。
- 不新增样式表里的时长、曲线与层级字面值；需要新值时先在 `packages/client/src/theme/tokens.json` 加一档。
- 不改变偏好默认值与设置页上的任何一行。
- 不改变动画的时长、曲线、起点与终点，不改变元素的盒、层级、文字、颜色与圆角。
- 不改变滚动位置的唯一写入者，不改变读者滚动时跟随让开的语义。
- 不把测量放进 `beforePaint` 订阅；测量仍只在帧管线的读阶段。

## 验收方法与目标

新增一个可重复的滚动场景 `scrollPace`，放在 `packages/testing/scenarios.mjs`，由同一份脚本完成三组动作：空闲 2 秒、滚动会话容器 4 秒、滚动窗口 4 秒。页面自己记录调度通行、每通行功能调用数、盒读取、样式读取、额外排帧、帧间隔与长任务；场景只读页面结果，判断值写进 `packages/testing/data/bounds.json`，并逐条写明理由。

建议的验收目标：

| 读数 | 目标 |
| --- | --- |
| 会话滚动触发的调度通行 | 0 |
| 会话滚动触发的皮肤盒读取 | 0 |
| 会话滚动触发的额外 `requestFrame` | 0 |
| 窗口滚动与窗口尺寸变化 | 已打开表面的位置与改动前一致；关闭表面不读盒 |
| 4 倍节流下的帧 p95 | 不超过 33 毫秒；若宿主自身基线已超过，改看“插件增量不超过一个 60 Hz 帧预算” |
| 4 倍节流下超过 33 毫秒的帧 | 不超过样本的 10% |
| 滚动阶段长任务总时长 | 不高于改动前；插件自身产生的长任务为 0 |
| 活动样式规则数 | 记录基线；会话页只保留常驻、对话列、输入卡与侧栏片段，数量不得上升 |
| 空闲 2 秒的调度通行 | 0 |

## 风险与约束

- 滚动与尺寸变化分开后，窗口滚动仍须重定位已打开的固定表面。验收必须覆盖打开弹层后滚动窗口、打开弹层后滚动会话、关闭弹层后滚动三类路径。
- 会话滚动器内部可能存在第三方插件插入的固定表面。实现时以“已打开表面的锚点是否位于滚动容器内”为准，不按滚动目标一刀切；皮肤自己的已知表面可以走快速路径，第三方表面走一般判定。
- 样式分片最大的风险是顺序与优先级。占位标签必须按构建时的 rank 顺序创建，片段只能填入与清空，不能移动标签；任何新增片段都要通过现有序检查与外观快照。
- 不把帧时间目标建立在单次样本上。每次改动至少运行三次 `scrollPace`，取中位数；同一台机器、同一棵树、同一浏览器版本下的前后对照才算数。
- 如果分片后的样式阶段没有下降，保留分片机制但不扩大分组范围；如果绘制阶段上升，先排查分片是否改变了合成层，再决定是否继续。

## 实施结果

本次工作只完成代码与可离线运行的门禁，端到端读数尚未采集：本机没有 `dsh` CLI（`dsh --version` 报 `Harness CLI not found`），`packages/testing/e2e.mjs` 在启动阶段退出，因此 `scrollPace` 的 `contentScroll`、`windowScroll` 与空闲读数没有有效样本。完成读数采集前，不把任何帧时间或盒读取数字写成验收结论。

已落地并验证的部分：

- 会话滚动与窗口尺寸变化拆成两条路径：会话滚动不排通行、不派发容器外的重定位；窗口滚动只通知声明 `repositionsOnScroll` 的打开表面；窗口尺寸变化保留 `measureReposition`、`reposition('viewport')` 与 `viewport` 通行。
- `view-tabs` 在 Windows 标题栏模式下跳过位移盒读取，批次挂载与每通行两条路径都只保留滑块需要的盒。
- 构建把主题样式表切成有序片段，运行时按组填充或清空占位标签；设置页与首页的片段按页面事实进入页面，会话页不携带这两组规则。共享卡片规则留在常驻组，关闭卡片的 `visibility` 与 `opacity` 基态因此始终可用。
- 重要性审计读取全部片段，再按构建顺序合并文本做规则编号；审计结束后逐片恢复原文。
