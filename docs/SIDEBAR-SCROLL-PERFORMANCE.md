# 侧栏拖动与会话滚动的卡顿根因和方案

本文件回答两个问题：打开侧栏并拖动改变宽度时，卡顿从哪里来；会话窗口滚动时，为什么仍比宿主原生体验差。它给出同一棵树上的测量、代码路径、解决方案、可见结果不变的依据与验收读数。机制写在模块注释里，方向性选择写在 `docs/adr/`，可执行的规则写进构建、lint 与测试。

长会话与流式输出的其余开销仍由 `docs/PERFORMANCE.md` 负责，滚动路由的整改仍由 `docs/SCROLL-PERFORMANCE.md` 负责；本文件只处理这两条输入与它们共用的样式匹配成本。

## 结论摘要

两个现象的成本来源不同，但共用同一个放大项。

1. 侧栏拖动时，宿主每帧重写整个框架的 `grid-template-columns`，侧栏宽度和手柄位置也随这一帧一起写。一次拖动因此让三列网格、侧栏内容与中线在每一帧重新排版。
2. 皮肤在宿主宽度写入之后继续工作：侧栏的状态功能订阅根节点 `style` 属性，`date-groups` 的侧栏观察者与 `manual-unread` 的侧栏观察者把同一批变更看成侧栏变化；输入卡、页脚与侧栏定位功能都声明了 `sidebar` 或 `composer` 为唤醒理由。拖动因此稳定产生“宽度写入 → 侧栏事实变化 → 侧栏功能同步”的固定链。
3. 样式表把上述重排放大。在 4 倍 CPU 节流、120 行会话、相同 DOM 与相同宽度写入的对照里，带皮肤样式时帧间隔 p95 为 33.3 毫秒、90 帧中 8 帧超过 33 毫秒；移除皮肤样式后 p95 回到 16.8～16.9 毫秒，样式重算从约 0.04 毫秒降到约 0.02 毫秒每轮。这是同一台机器上的直接对照。
4. 会话滚动时，行级 `content-visibility` 已把离屏对话行移出排版；轨道上的滚动监视也已在 `content` 滚动时跳过窗口重定位。剩余成本集中在滚动容器内可视节点与常驻样式规则的匹配，以及阅读器接管、跟随与导航在滚动帧内的少量读写。
5. 两项整改都必须以“可见结果不变”为前提：同一会话、同一偏好、同一窗口尺寸下，元素盒、文字、颜色、圆角、层级、动画时长与曲线、命中区域与键盘路径保持原样。

## 根因

### 根因一：拖动是一条每帧重写三列的宿主路径

`@deepseek-ai/dsh-client-ui-layout` 的 `DragHandle` 以指针捕获和 `requestAnimationFrame` 合并拖动位移；`AppFrame` 用 `cols.sidebar`、`cols.rightbar` 与 `viewport` 计算三列，并把结果写到框架的内联 `grid-template-columns`。`onSidebarDrag` 每帧调用 `actions.setSidebar(sidebarBase.current + dx)`；`setSidebar` 在 store 中更新 `layoutInfo.sidebar`。

宿主侧栏自己的 `SidebarRoot` 也把宽度写在根节点内联 `style` 上；拖动侧栏时，宿主把 `data-dragging` 写在框架上；侧栏根节点仍会在每一帧读到新的 `width`。

因此一次拖动至少有三种宽度写入落在同一帧：

- 框架的 `grid-template-columns`；
- 侧栏根节点的内联 `width`；
- 侧栏手柄的 `left`。

其中第一项会同时改变侧栏、中心和右侧三列的轨道；后两项让侧栏内部的内容与中线一起参与重排。这是宿主的设计，本插件可以处理的是自己在这条写入之后增加的同步与样式匹配。

### 根因二：皮肤的侧栏观察者把宽度写入当成侧栏事实变化

`packages/client/src/features/sidebar-status/sidebar-status.ts` 在侧栏根节点上订阅：

```ts
subscribeMutations(root, {
  childList: true, characterData: true, subtree: true,
  attributeFilter: [
    SESSION_PHASE_ATTRIBUTE, PART_ATTR, 'hidden',
    'aria-hidden', 'contenteditable', 'style', 'class',
  ],
}, schedule)
```

`style` 在订阅的过滤里，而根节点的宽度正是宿主每帧改写的内联 `style`。一次拖动因此会持续产生 `sidebar` 理由的调度请求；该功能随后在每次通行中遍历侧栏行、读取标题的 `getComputedStyle`、`getBoundingClientRect` 与可见性。

同一类放大还有两处：

- `packages/client/src/shared/sidebar-watch.ts` 用 `childList: true, subtree: true, skipQuiet: true` 整页观察，并把落在侧栏内的目标交给请求；`date-groups` 使用它。它不把宽度写入当内容变化，但当侧栏行在重排中被宿主替换时，会把它算作侧栏变化。
- `packages/client/src/features/manual-unread/manual-unread.ts` 也在侧栏根节点上订阅，过滤器为 `subtree: true, attributeFilter: ['aria-selected', SESSION_ROW_KEY_ATTRIBUTE]`；这一处不读宽度；侧栏结构变化会让它与其他 `sidebar` 理由句柄一起同步。

侧栏状态功能的 `wakesOn: ['sidebar', 'composer']`、页脚的 `wakesOn: ['sidebar', 'composer']`、日期分组的 `wakesOn: ['sidebar']`、手动未读的 `wakesOn: ['sidebar']` 与侧栏条目的 `wakesOn: ['sidebar']` 因此会在拖动中反复执行。窗口尺寸变化另有 `viewport` 理由的句柄；拖动与窗口尺寸变化属于两套唤醒集合，两者的读数要分别采集。

### 根因三：样式表在拖动帧内是全量参与者

替代宿主样本的对照已经给出直接证据：移除皮肤样式后，同一拖动脚本的帧 p95 从 33.3～33.4 毫秒回到 16.8～16.9 毫秒，超过 33 毫秒的帧从 7～11 降到 2～4，样式重算从 0.037～0.099 秒降到 0.016～0.021 秒。排版次数与拖动写入次数不变（86～87 次），说明样式开关没有改变宿主每帧重写三列这一事实；它改变的是这 86 次排版中浏览器需要为可视节点匹配多少规则。

样式规模表中常驻四组共 1,663 个选择器。侧栏与会话里大量规则以 `body[data-dsh-claude-style]` 为前缀，并大量使用 `:is()` 与属性选择器；侧栏行规则同时在 `theme/sidebar.css`、`sidebar-status`、`workspace`、`manual-unread` 与 `date-groups` 中出现。

这里必须保持因果边界：样式表开关同时移除了可见外观，绘制路径会变；样式阶段的差值要作为成本归属的证据，帧时间收益以同外观前后对照为准。它的作用是证明“样式匹配规模是拖动帧的放大器”。整改后样式表在拖动期间仍要画出同样的外观，同时减少参与匹配的规则。

### 根因四：会话滚动的主要余量在样式匹配与滚动帧内的固定工作

会话滚动的现状与 `docs/SCROLL-PERFORMANCE.md` 记录的整改方向一致，但上一轮整改后仍有两个未覆盖点：

- 会话滚动已经不再唤醒整页调度通行；`packages/engine/src/scheduler.ts` 的 `isContentScroll()` 排除了会话容器内的滚动，`noteScroll()` 只处理已被滚动主人持有的容器。这解决了“每次滚轮一次整页通行”的主因。
- 滚动帧仍要匹配会话页常驻的约 1,663 个选择器；滚动容器内可视行的样式、伪元素与常驻动画由浏览器逐帧处理。替代宿主样本在 120 行长会话上滚动 160 帧没有出现长任务，说明当前路径没有功能自激，但真实桌面窗口的合成与字体差异会把这部分成本放大。
- 滚动帧内仍有一些固定读写：跟随按钮、等待行与折叠相关功能在滚动时会被唤醒；`chat-follow` 的 `wakesOn: ['content', 'composer', 'viewport']` 与 `chat-fold` 的同类声明会在 `viewport` 理由下执行，内容滚动本身不再触发它们，但窗口滚动与尺寸变化仍会触发。

滚动问题要让滚动路径只承担“本次滚动真正改变的画面”，并让常驻规则更少。新增滚动监听或放大 `content-visibility` 都不触及这两项成本。

### 根因五：拖动与滚动的共同放大器是常驻规则面

拖动与滚动在浏览器侧共用的成本是样式匹配、布局与绘制。`part-sizes.json` 给出常驻四组的规模，`realistic-av-css.mjs` 与 `standin-drag-styles-onoff.mjs` 给出样式开关的对照，`standin-cv-toggle.mjs` 给出滚动时行级跳排已经承担的作用。

当前分组还存在一处结构性浪费：会话页同时常驻 `sidebar` 组，但侧栏对会话滚动没有可见作用；侧栏拖动又需要 `sidebar` 组与 `conversation` 组同时参与，因为中心列宽度随拖动改变。分组按“输入会改变哪些表面的盒”来定，简单按页面二分会把会话滚动带入侧栏规则。

## 解决方案

方案由五项互不替代的整改组成；每一项都可以单独验收，也都必须以可见结果不变为前提。它们没有先后依赖，可以并行实现与评审。

### 一、把侧栏宽度写入与侧栏事实分开

**改法**：侧栏状态功能的根节点订阅不再把 `style` 当作侧栏事实。宿主的宽度写入走 `width` 一个属性；侧栏行变宽后真正需要重读的是标题盒、状态标记与行的可见性，而这些已经由行的结构变化、状态属性变化和尺寸观察提供。把 `style` 从 `attributeFilter` 中移出，并在确实需要跟随宽度时改用 `observeSize` 的宽度回调，回调内只比较宽度是否真的变化。

**为什么可见结果不变**：`style` 过滤器原本用于捕捉宿主重建行时写入的内联样式，以及侧栏根节点的宽度；前者若同时伴随子节点或类名变化，现有过滤器仍能听到，后者由尺寸回调覆盖。状态标记、行状态与标题可见性仍然在同一帧的读阶段与写阶段执行，写出的属性与写入时刻不变。

**验收**：

- 机制层：侧栏根节点只改 `style.width` 时，`sidebar-status` 的 sync 不增加；侧栏行插入或 `data-state` 改变时，sync 仍执行。
- 行为层：侧栏行尾状态标记、标题可见性、进行中的三种外观在拖动前后与改动前一致。

### 二、让拖动期间只同步真正依赖宽度的表面

**改法**：给调度器的 `WakeReason` 增补一个明确的 `sidebar-width` 理由，与现有 `sidebar` 并列，分别表示宽度变化与结构变化。宽度的每一帧只唤醒确实需要重新测量盒的功能：输入卡响应式、页脚账户行宽、上下文统计的适应宽度、侧栏状态标题的可见性、工作区分段控件的滑块。日期分组、手动未读与侧栏入口的偏好隐藏等只依赖结构与状态的句柄不因纯宽度变化而被唤醒。

**为什么可见结果不变**：被唤醒的集合只包含需要宽度读数的句柄；不依赖宽度的句柄在纯宽度变化上读到的结果与上一帧相同，跳过它们的 sync 不改变任何写出的标记。结构变化仍使用原来的 `sidebar` 理由，因此行的增删与重新排序仍会唤醒这些句柄。

**验收**：

- 机制层：仅宽度变化时，`date-groups`、`manual-unread`、`sidebar-entries` 的 sync 不执行；`composer` 的响应式测量、页脚的账户行盒测量仍执行一次。
- 行为层：拖动前后，侧栏行顺序、日期分组、未读标记、面板隐藏与“更多”菜单位置一致。
- 拖动样本：每帧调度通行从当前值降到只包含宽度依赖句柄的通行，盒读取次数不高于改动前。

### 三、让侧栏宽度与手柄位置逐帧跟随指针

**改法**：皮肤在侧栏手柄的按下与释放上维护自己的拖动期标记（`data-dsh-claude-sidebar-dragging`）。框架的三列、侧栏自己的宽度与手柄的 `left` 在拖动期间照常逐帧换算；依赖侧栏宽度的内容测量（工作区分段控件、页脚账户行、输入卡工具栏、统计行与面板、会话行的跳排往返）在标记期间暂停，释放后由 `sidebar-width` 的通行一起补齐。

**为什么可见结果不变**：拖动过程中侧栏边界与手柄跟随指针；最终盒、文字换行、截断与中线位置与改动前相同。拖动期间变化的是哪些内容在中间宽度上重新排版，以及什么时候重新排版。

**为什么不能用“按住期间保留宿主原值”**：页面缩放在 body 上写 `zoom`，宿主的宽度写在缩放空间里，屏幕上的侧栏宽度是宿主宽度乘以缩放倍数。按住期间保留宿主原值会让 125% 下的侧栏比指针多走 25%，也让手柄离开它要拖的边界，这正是“不跟手”的来源。拖动期的处理只挂在内容的测量上，宽度与手柄位置继续逐帧换算。

**验收**：

- 行为层：拖动过程中侧栏边界与手柄跟随指针；拖动结束后侧栏内容宽度、标题截断、行高与中线位置逐像素一致。
- 拖动样本：同一拖动脚本下布局次数与样式重算次数下降，帧 p95 回到 16.8～16.9 毫秒；超过 33 毫秒的帧为 0。
- 页面缩放：在 80%、100%、125% 三个缩放下，拖动期间侧栏与手柄的位置逐帧等于指针所在的边界。

### 四、让样式分组按输入影响范围挂载

**改法**：保留现有七组占位标签与构建顺序，把 `shared/popover.css` 的两种职责拆开：

- 关闭态基态（不可见、无指针事件、无合成层）进入 `base` 常驻组；
- 打开态卡片外观与弹层行样式进入 `popover` 组，只在卡片打开时挂载。

会话页仍需要侧栏组，因为侧栏一直显示；会话滚动本身已经按会话容器分流，不会请求整页通行。样式分组整改只处理弹层两组职责的拆分与常驻规则规模的下降，侧栏组继续常驻。

**为什么可见结果不变**：规则文本、顺序、选择器与优先级不变；只是关闭的弹层不再把打开态规则带进会话页。关闭态基态仍在常驻组，关闭卡片仍不可见、不可点、不占合成层；打开卡片时 `popover` 组进入页面，卡片的外观与动画与改动前相同。

**验收**：

- 行为层：`popover-parts` 规范要求打开卡片后 `popover` 组进入页面，其他组顺序不变；关闭后卡片 `visibility` 为 `hidden`、`opacity` 为 `0`。
- 外观快照：明暗两套截图、`appearance.json` 与 `importance` 场景与改动前一致。
- 样式规模：会话页常驻字符数、规则数与选择器数下降；`popover` 组在打开卡片时非空，关闭动画结束后清空。
- 拖动样本：同一拖动脚本下样式重算总时长下降，帧 p95 不高于改动前。

### 五、把滚动路径的验收固定到两个读数

**改法**：现有 `scrollPace` 场景已经登记在 `packages/testing/scenarios.mjs` 与 `packages/contracts/src/timing.ts`，但没有真实宿主读数。整改后必须在真实桌面窗口上补齐以下读数，并把上限写进 `packages/testing/data/bounds.json`：

- 会话滚动触发的调度通行数；
- 会话滚动触发的皮肤盒读取次数；
- 会话滚动触发的额外 `requestFrame` 次数；
- 窗口滚动与窗口尺寸变化的已打开表面位置；
- 4 倍节流下的帧 p95、超过 33 毫秒的帧数与长任务总时长；
- 会话页活动规则数与常驻样式字符数。

**为什么可见结果不变**：这些读数只观察页面自己的计数与真实帧时钟，不改变任何样式、动画或交互；上限只用于验收判断。

**验收**：真实宿主上同一会话、同一脚本、同一窗口尺寸下，改动前后的中位数对照；三次运行取中位数，不把单次样本写成结论。

## 改动边界

- 不新增 `MutationObserver`、`ResizeObserver` 或 `requestAnimationFrame`；新的观察登记走 `packages/engine/src/bus.ts`，新的排帧走 `packages/engine/src/frame.ts`（D40）。
- 不新增对宿主服务的按名读取；需要新数据时在 `packages/engine/src/host.ts` 加访问器，并在 `packages/contracts/src/table.ts` 登记（D3）。
- 不新增样式表里的时长、曲线与层级字面值；需要新值时先在 `packages/client/src/theme/tokens.json` 加一档（D9）。
- 不改变偏好默认值与设置页上的任何一行。
- 不改变动画的时长、曲线、起点与终点，不改变元素的盒、层级、文字、颜色与圆角。
- 不改变滚动位置的唯一写入者，不改变读者滚动时跟随让开的语义。
- 不把测量放进 `beforePaint` 订阅；测量仍只在帧管线的读阶段。
- 侧栏拖动期间不写 `scrollTop`，不改变宿主的拖动指针捕获与手柄命中区域。


验收目标以同机前后中位数为准：

| 读数 | 目标 |
| --- | --- |
| 侧栏拖动帧 p95 | 不超过 16.9 ms；若宿主原生基线高于此值，插件增量不超过一个 60 Hz 帧预算 |
| 侧栏拖动超过 33 ms 的帧 | 0 |
| 侧栏拖动布局次数 | 不高于宿主每帧写入次数；插件自身不额外增加布局 |
| 侧栏拖动样式重算总时长 | 低于改动前中位数 |
| 会话滚动触发的调度通行 | 0 |
| 会话滚动触发的皮肤盒读取 | 0 |
| 会话滚动触发的额外 `requestFrame` | 0 |
| 会话页常驻样式字符数 | 低于改动前 |
| 会话页常驻选择器数 | 低于改动前 |
| 4 倍节流滚动帧 p95 | 不超过 33 ms；若宿主基线已超过，插件增量不超过一个帧预算 |

## 风险与约束

- 侧栏拖动的中间状态由宿主的布局结果决定，插件的整改范围是“皮肤自己的同步与样式”。宿主的 `grid-template-columns` 写入属于宿主的布局路径。
- 把侧栏宽度写入从 `style` 过滤器中移出时，必须保留宿主重建行时的其他触发路径；仅靠宽度回调无法覆盖行节点被替换的情况。
- 样式分组拆分必须以关闭态基态常驻为前提；把整张 `shared/popover.css` 移入 `popover` 组会让关闭卡片在关闭动画结束后露出内容。
- 拖动期间暂停内部换行必须保证拖动结束后的最终布局与改动前逐像素一致；任何缓存或延迟落布局都要在拖动取消、指针丢失、窗口尺寸变化与页面隐藏时清除。
- 会话滚动的读数必须在真实宿主上取；替代页面的 16.8 ms 证明路径没有自激；桌面窗口的合成与字体成本要由真实读数回答。
- 不把单次样本当结论；同一拖动脚本、同一会话、同一窗口尺寸至少运行三次，取中位数；样本之间的差异不写进产品代码。
